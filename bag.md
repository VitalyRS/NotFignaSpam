# Баг: Пропуск новых пользователей через спам-фильтр и бан за разрешенные теги

## Описание проблемы 1: Бан за разрешенные теги
Новые пользователи получали бан (рестрикт) в топиках `ads` и `parcels` при использовании разрешенных тегов (например, `#квартира`). Бот воспринимал эти теги как `Entities (ссылки/форматирование)` и банил пользователя, так как для новых участников любые entity по умолчанию запрещены.

## Описание проблемы 2: Пропуск карантина после рестарта
Пользователь `ANGEL` написал в чат через 2 часа после входа, но спам-фильтр не применил к нему ограничения нового пользователя.
Это происходило из-за того, что список новых пользователей (`new_users`) сохранялся из оперативной памяти в базу данных только раз в час или при штатном завершении работы бота. Если сервер (например, Render) перезапускал приложение до срабатывания таймера, новые пользователи пропадали из карантинного списка в памяти и воспринимались ботом как старые (проверенные) участники. Кроме того, счетчик `clean_messages` вообще не сохранялся в БД.

## Решение
1. **Фильтрация тегов**: Добавлено исключение для тегов (`hashtag`) в проверке `entities` для топиков `ads` и `parcels`. Ссылки и пересылки по-прежнему запрещены.
2. **Мгновенное сохранение в БД**: При каждом изменении состояния пользователя (добавление, изменение статуса, счетчик чистых сообщений) триггерится немедленное сохранение в БД (`save_user_state`).
3. **Безопасный UPSERT**: Запрос сохранения пользователей в БД переписан с `TRUNCATE TABLE` на `INSERT ... ON CONFLICT DO UPDATE`, чтобы изменения можно было безопасно и конкурентно записывать прямо во время работы бота.
4. **Сохранение чистых сообщений**: Добавлена колонка `clean_messages` в БД, и теперь счетчик корректно сохраняется и восстанавливается после перезагрузки.

# Фича: Команда `/nolim` для снятия флуд-контроля

## Описание
Существовала проблема, когда пользователи попадали во флуд-контроль (лимиты на отправку сообщений по времени) в специфичных топиках типа `ads` (объявления) и `parcels` (посылки). Администраторам требовался быстрый способ вручную снимать эти ограничения для конкретного пользователя сразу в обоих топиках.

## Решение
1. Добавлена новая команда `/nolim <ID_пользователя>`.
2. Команда доступна только администратору (`master_id`).
3. При вызове команда вызывает очистку записей в таблице `topic_limits` базы данных для данного пользователя по темам `ads` и `parcels`.
4. Обновлено справочное сообщение `/help`, чтобы отразить наличие новой команды.
